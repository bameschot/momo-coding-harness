A coding assistant that stays on your machine.

momo connects to a local Ollama or llama.cpp server and gives the model tools to read, search, edit and run your project. Use it from a split-pane terminal UI, a browser window, or both at once. It runs on the Python standard library in about 40 MB of RAM, and it sends nothing anywhere except to the model server you point it at (and any MCP servers you add yourself). A small black cat keeps you company.

What it does

Everything below works offline against a model you run yourself. Each card links to the detailed documentation further down this page.

Ollama or llama.cpp, local or remote

Point momo at an Ollama server or a llama.cpp llama-server, on your own machine or a GPU box elsewhere. Pick one with --provider and --host, move between servers with /host, and add a Bearer token with /token for a server behind a proxy. Every mode, tool and UI works the same on both.

Lightweight by design

Python standard library only, with no Node, build step, database or daemon. Two optional packages (tree-sitter grammars for code navigation, pypdf for PDFs) take about 22 MB. momo uses about 40 MB of RAM idle and 90–130 MB with the code index on; the model's memory lives in Ollama or llama.cpp.

Guarded internet access

MCP servers

Plug in any Model Context Protocol server, a local command or a remote HTTP endpoint, in the same mcpServers format Claude Desktop uses. Its tools and resources join momo's own. Tools that change things ask first, and a project's .mcp.json never runs until you approve it.

Tools a project brings along

Commit tools in .momo/tools/ and the whole team gets them. Each runs in its own process with the project's own virtualenv, gets its modes from its category, and never runs before you approve it. A shipped guide lets an agent write them for you.

Your code goes only to your model

momo talks to one server: the Ollama or llama.cpp you point it at. No telemetry, accounts or update checks, and the web UI loads nothing from the internet. The internet tools stay off until you turn them on, and MCP servers only run when you configure them. With a local model server, nothing leaves the machine.

Getting started

Requirements

  • macOS or Linux. The terminal UI uses Python's built-in curses, which Windows lacks; on Windows, use WSL.
  • Python 3.14+. No packages are required; requirements.txt only adds features (see Requirements & footprint).
  • A model server on this machine or another: either Ollama, or a llama.cpp llama-server with Jinja chat templates enabled, which tool calling needs. Current builds enable them by default; on older builds, pass --jinja.
  • A model that can call tools. A 9B model such as qwen3.5:9b with a context window of 32k tokens or more is a good start; the evals on this page were run on it. Bigger models (qwen3-coder:30b) follow multi-step tasks more reliably. Models without tool support can only chat.

Run

bash
python momo-coding-harness.py                     # TUI + web UI on 127.0.0.1:8765

# a local llama.cpp server
python momo-coding-harness.py --provider llamacpp --host http://localhost:8080

The provider and host are remembered for the next launch. Running against a backend has step-by-step setups for local and remote Ollama and llama.cpp; Command-line flags lists every option.

Your first session

  1. Check the startup line. momo prints the model, its context window and the web UI address. If the model is marked offline, momo can't reach the server: check --host.
  2. Describe what you want. momo starts in design mode, which reads the code and asks questions but changes nothing except the design document it writes. That makes it a safe first conversation in an unfamiliar project.
  3. Switch mode to act on it. Shift+Tab or /code for a direct change, or /plan to have momo plan it first and wait for your y. See Modes.
  4. Pick it up later. The session is saved after every reply, and the next launch restores it. --fresh or /new starts over.

Remote servers

"Remote" means --host points somewhere other than localhost: a machine on your LAN, a GPU box, or a hosted endpoint behind a reverse proxy. The tools and your files stay on the machine running momo, but each request goes to the server: your messages, the system prompt, and whatever the model has read or run, including file contents and command output. Use a server you trust with your code.

  • Give the full URL, including the scheme: http://192.168.1.10:11434, not 192.168.1.10:11434.
  • Prefer an SSH tunnel to exposing the model port. ssh -L 11434:127.0.0.1:11434 gpu-box (or 8080 for llama.cpp) lets momo use the default localhost host, and the server stays unreachable from the network. Proxy environment variables (HTTP_PROXY …) aren't used, so a tunnel is also the way through a jump host.
  • Plain HTTP unless the URL is https://. HTTPS servers are verified against the system's certificate store. Put a TLS-terminating proxy in front of a server you reach over an untrusted network, especially if you send a token.

When it doesn't connect

  • Check the status bar. It always shows the provider (VIA: ollama), host and model, and the startup line says which context window was detected.
  • Server down? The TUI shows (offline) after the model, the web UI shows · offline and an orange connection dot, and /host <url> answers "(not reachable)". momo checks again before every message, so restarting the server is enough.
  • No context window detected? Set one with --context 16384.

Requirements & footprint

momo is meant to sit beside your editor and use very little of the machine. The model is what needs real memory: a 9B model quantised to 4 bits typically takes several gigabytes of RAM or VRAM in Ollama or llama.cpp. momo adds only the figures below, and nothing at all for the model if it runs on another machine.

How momo works

There are three parts: you, momo (the harness, running on your machine) and the model server. You send a message; momo sends it to the model together with a system prompt (instructions for the current mode) and the tool schemas (what the model may call). The model answers in text, or asks for tools: read a file, search, edit, run a command. momo runs those in your working directory and sends the results back, until the model answers in text.

  • Modes decide which tools are offered and what the system prompt says. See Modes.
  • Context is everything sent in one request. The CTX meter shows how full it is, and old parts are summarised when it fills up. See Context & compaction.
  • "momo" is the app, one of its modes and the cat on the input bar.

Modes

Cycle with Shift+Tab (design → chat → plan → coding → momo), or switch directly with /design, /chat, /plan, /code or /momo. Each mode swaps the role prompt and the set of tools offered to the model.

Which one? Not sure yet what to build: design. Questions about code or documents: chat. A change that touches several files, or one you want to review before it happens: plan. A change you can describe in a sentence: coding. momo starts in design because it can't change your code, which makes it a safe default in a project it hasn't seen.

Plan mode

For changes you want to see before they happen. momo investigates, writes a step-by-step plan to .momo/plan.md, and changes nothing until you approve it.

There are two kinds of plan, and both follow the lifecycle below:

  • Normal (/plan or /plan normal, the default). Each step says what to change and how to check it. The last step runs the project's tests, and the model reports when a step is done.
  • Test-driven (/plan tdd). Every step also lists the outcomes that prove it works, and those become tests before any code is written. The harness then runs the suite itself at the end of each step and only moves on when it passes. See Test-driven plans.

The choice is saved with the session. The status bar shows plan (tdd), and in the web UI a normal plan / TDD plan selector sits next to the mode picker while you're in plan mode. It is locked while a plan runs; a draft that isn't approved yet takes the new type the next time the model submits it.

  1. Investigate. The model follows the code the change touches, reproduces a bug if there is one, finds out how the project is tested, and asks you only what would change the plan.
  2. Plan. create_plan writes a goal and ordered steps to .momo/plan.md; each step names the file and function, the change and how to verify it.
  3. Confirm. y runs it, n keeps it for /plan run, and anything else is feedback the model revises it with. You can edit the file by hand first; [-] skips a step.
  4. Execute. Approving switches to coding mode, which runs the plan with its own tools and loaded skills and stays on when the plan is done. One step at a time, with the plan (▶ on the current step) in the system prompt so the model keeps its place even after compaction. revise_plan replaces the remaining steps. A paused plan carries on with /plan resume or any message, even after a restart.

You can edit .momo/plan.md freely before approving: reword or reorder steps, add or delete them, or mark one [-] to skip it. In a test-driven plan the expectations show as Expect: lines, and you can edit those too.

Test-driven plans

A normal plan trusts the model to say when a step is done. A test-driven plan doesn't. Before any code is written, the expected outcomes of every step, and of the change as a whole, become tests. Each step must then make its own tests pass, and the harness runs the suite to check. Tests for steps that aren't implemented yet are skipped, so they never break the build. They start to count when their step begins.

What the plan holds

Besides the usual goal and steps, create_plan asks for:

  • test_command: the command that runs the whole suite and exits non-zero on a failure, e.g. python -m pytest -q. The model finds it during investigation and runs it once to see that it works.
  • tests on every step: the outcomes that prove the step works, each written as input or action → expected result, e.g. remove("apple", 3) when 2 are in stock → ValueError, count still 2.
  • acceptance: the outcomes of the whole change, seen from the user's side.
  • Optional step_test_command for a slow suite. See Slow suites.

The harness wraps the model's steps in two stages of its own and gives every step a fixed tag, tdd-step-1, tdd-step-2 and so on, plus tdd-acceptance. The tags stay put when revise_plan reorders the steps, so the tags already written into test files stay right. A step the model adds later gets a new tag and is told to write its tests first. A step that only runs or checks the tests, such as "Run the full test suite", "Keep existing tests green" or the planner's own "Acceptance", is dropped with a note, because the plan already does that at every step.

Skip markers

Pending tests use the test framework's own skip, on its own line directly above a complete test, with the tag in the reason:

FrameworkMarker
Python unittest@unittest.skip("tdd-step-2")
pytest@pytest.mark.skip(reason="tdd-step-2")
JUnit@Disabled("tdd-step-2")
Rust#[ignore = "tdd-step-2"]
Got.Skip("tdd-step-2") as the first line of a complete test
Jest, Vitest, Mochait.skip("adds (tdd-step-2)", …)

When a step starts, the harness deletes the marker lines with that step's tag itself. A line that also opens the test, like the it.skip(…) form, is left for the model to change, and the step's instructions name it. A test whose body is only its skip marker checks nothing, so the gate after the test-writing stage refuses it. In compiled languages the model may add minimal stubs (a signature that raises "not implemented") so skipped tests still compile.

What the gate checks

StageBefore the suite runs
Writing the testsEvery step's tag and tdd-acceptance appear in the project. No marker sits on an empty test. (Leaving production code alone, apart from stubs, is asked of the model, not checked.)
A stepThis step's tag, and the tags of all earlier steps, are gone. No check (assert…, expect…) was deleted from a test. No test of a finished step changed.
AcceptanceNo tdd- tag is left anywhere.

Then test_command must exit 0. Approving a test-driven plan also approves running that command after every step, without a run_command confirmation. The tags are found by searching the project's text files. .momo/plan.md and momo's own logs are skipped, since the test output in them repeats the skip reasons.

  • Test changes are audited. When the tests are written, the harness notes which test belongs to which step, and at each gate it compares the test files with how they were when the step started. A deleted check is refused, and so is a change to a finished step's test. Any other change, such as an expectation the model got wrong and corrected, is listed in the chat as Test lines changed in step N. If an expectation itself is wrong, the model is told to say so or ask you, never to weaken the test.
  • Three refusals in a row ask you. If the same step fails its gate three times, momo asks for guidance to pass on to the model, or pause to stop the plan there. Resume with /plan resume.
  • A text reply doesn't skip the gate. A step the model ends with a plain answer instead of complete_step is gated too. After two more failed attempts the plan pauses.
  • Tests that already pass. If a step's tests pass the moment they are switched on, the model is told so. If the step needs no code change it says so and finishes; otherwise it first makes the tests check the new behaviour.

Slow suites

Each stage runs the suite at least twice: the red check when its tests are switched on, and the gate. Two things keep that down when the suite is slow:

  • A step test command. A plan may give step_test_command with {files} (the stage's test file paths), {dirs} (their directories, as ./dir) or {stems} (their names), e.g. python -m pytest -q {files} or go test {dirs}. The harness fills it in from the stage's real test files and uses it for the red check, and the step's instructions offer it to the model. The full suite stays the gate. The template is tried once, right after the tests are written. One that fails while everything is still skipped (wrong runner, no matching file) is dropped with a note.
  • Reusing the model's own run. If the model's last command was the plan's test_command (verbosity flags such as -v aside), it passed, and nothing was written since, the gate uses that run instead of running the suite again. Its result says your run of … just before. A trailing | tail -N doesn't stop this, because run_command takes it off and keeps the real exit code. Any other pipe does.

What it costs

Measured end to end with evals/tdd_bench.py against a 9B model on llama.cpp: a two-feature change to a small class, a hidden checker of 8 cases, 3 runs per setting. Every run of both kinds was correct. A test-driven plan took about 8 minutes against about 6 for a normal plan, and wrote two to three times as many tests. With a planted 20-second test in the suite, the harness's own test time per run fell from 141 s to 80 s, and 9 of 12 gates reused the model's run. The extra time also buys something: in these runs the red-to-green loop caught wrong expectations the model had written into its own tests, such as an off-by-one threshold or insertion order where sorted order was asked for. The audit now lists each such correction in the chat. The full tables are in evals/README.md.

Web UI

It starts with the TUI at http://127.0.0.1:8765, reachable from this machine only (--headless runs it alone, --no-web turns it off). It loads nothing from the internet, so it works fully offline. To open it from another device, see Access & security.

One session, two windows

  • Messages, replies, tool calls and diffs appear in both the browser and the terminal.
  • A question from the model can be answered in either window.
  • Mode, model, host, context and plan progress are shared. View options, such as hiding thinking, are per window.
  • Reloading the page replays the conversation so far.

What's in it

  • Status bar:
    • the session drawer (load, start or delete sessions) and a workspace file browser;
    • mode and model pickers;
    • the CTX meter: click it for the per-category breakdown and a link to the system prompt;
    • THINK / RUN / NET / INDEX badges for those settings;
    • a plug button for MCP servers (with a count of connected servers) a wrench button for this mode's tools, and a book button for skills (with a count of active ones).
  • Transcript: streamed markdown replies, collapsible thinking, one-line tool calls that expand to show arguments and results, coloured diffs and question cards with Yes/No buttons.
  • Input: / command autocomplete, @ fuzzy path search, a queue for messages sent while the model is busy, and Retry / Edit on your last message.
  • Attachments: drag, paste or pick files. Text and PDFs are converted to text. Chips show a token estimate and turn amber when a file would use more than a quarter of the context.
  • Notifications: a synthesised kitten mew (rising for a question, falling when a turn ends) and an optional desktop notification when the window isn't focused.
  • Syntax highlighting for about 20 languages, copy buttons on code blocks, and light and dark themes.

How tools are built

Every tool the model can call is one Python file. The file declares everything momo needs to know about the tool: the schema the model sees, the function that runs, when the tool is offered and how the harness treats a call. Nothing else lists tools by hand. The per-mode tool sets, the tool reference in the system prompt, the /tools pickers and the tables the harness checks (which tools show a diff, which keep a TDD plan's passing tests valid, which can't be turned off) are all read from these files. Adding a tool means adding a file, for a built-in tool and for your own alike.

Anatomy of a tool file

A built-in tool, shortened: delete_file.py. A tool file has three parts: the function, the schema, and the Tool that ties them together with how the harness treats the tool.

harness/tools/builtin/delete_file.py
"""delete_file: remove one file (never a folder)."""
from pathlib import Path

from ...paths import safe_entry_path
from ..registry import Tool, tool_schema


# 1. The function: the model's arguments, plus workdir; returns the text the model gets back.
def delete_file(path: str, *, workdir: Path) -> str:
    p = safe_entry_path(path, workdir)          # an ERROR string when the path leaves the workdir
    if isinstance(p, str):
        return p
    ...
    return "OK"


TOOL = Tool(
    # 2. The schema: exactly what the model sees.
    tool_schema("delete_file",
        "Permanently delete a single file (this cannot be undone). ...",
        {"path": {"type": "string", "description": "File to delete"}},
        ["path"]),
    # 3. How momo offers it and treats a call.
    run=delete_file,
    order=470,                  # its place in every tool list
    group="edit & shell",       # its section in the /tools pickers
    writes=("path",),           # re-index this path after the call
    diff=True,                  # the frontends show what changed
    example={"path": "old-file.py"})   # the example call in the tool reference

The schema text is load-bearing: it is the only thing the model knows about the tool, and a small model picks tools by the first sentence of the description. modes is left at its default here, so delete_file is offered in coding mode, momo mode and a running plan, and nowhere else.

One tool, several schemas

Some tools look different depending on the session. run_command has two schemas: in /run-mode new it takes tail, grep and background and saves the output to a log, and in classic mode it only takes command and timeout. create_plan asks for a test command and expected outcomes in a test-driven plan. Adding a built-in tool

  1. Add harness/tools/builtin/<name>.py, named after the tool, ending with TOOL = Tool(...).
  2. Pick an order in the group's range; the gaps of 10 leave room.
  3. Run the tests. tests/test_tool_registry.py checks that every file defines one tool named after it, that the orders are unique, that every schema argument and injected value reaches the function, and that each example fits its schema.
  4. A new tool changes what the model sees, so tests/test_tool_registry_golden.py fails on purpose. It pins every schema, the tool reference and the system prompt across 192 combinations of mode and settings. Regenerate it with MOMO_REGEN_GOLDEN=1 once the change is meant.

Your own tools

Put a tool file in ~/.momo-harness/tools/. momo loads it at start and on /tools reload, and it shows up in the mode's tool list, the tool reference and the /tools pickers under "custom", where you can turn it off per mode like any other tool. The same Tool class applies, imported from harness.tools. A complete example, docs/examples/tools/word_count.py:

~/.momo-harness/tools/word_count.py
from pathlib import Path
from harness.tools import ALL_ROLES, Tool, read_text, tool_schema

def word_count(path: str, *, workdir: Path) -> str:
    got = read_text(path, workdir, refuse_binary=True)   # stays inside the workdir
    if isinstance(got, str):
        return got                                       # an "ERROR: ..." the model can act on
    _, text = got
    return f"{path}: {len(text.splitlines()):,} lines, {len(text.split()):,} words"

TOOL = Tool(
    tool_schema("word_count",
                "Count the lines, words and characters of a text file in the project.",
                {"path": {"type": "string", "description": "File to count, e.g. 'README.md'"}},
                ["path"]),
    run=word_count, modes=ALL_ROLES, keeps_green=True, example={"path": "README.md"})

Tools a project brings along

A repository can carry its own tools in .momo/tools/, committed and shared with everyone who opens it. They are self-contained, run in their own process, and never run before you approve them. See Workspace tools.

Writing a tool a small model uses well

  • Lead with what it is for. The first sentence of the description is how a small model chooses. A feature mentioned only at the end of a parameter description got used 7 times in 15; named up front, 3 in 3.
  • Return errors it can act on. Start with ERROR: and say what to do instead: the path that would work, the argument that is missing.
  • Keep results bounded. Cap long output, say what was left out, and point at how to get the rest.
  • Hint in the result, not the prompt. A pointer to the next useful call, inside the tool's own result, steered the 9B more reliably than any rule in the system prompt.
  • Honour Esc. A slow tool takes inject=("cancel",) and stops when cancel.is_set().

Workspace tools

A project can bring its own tools. Put them in .momo/tools/ and commit them, and everyone who opens the repository in momo gets them: a report generator, a check against the team's conventions, a wrapper around the project's own scripts. They follow the same structure as the built-in tools, with two differences. A workspace tool is self-contained: it never imports momo's code and runs in its own process. And because it arrives with a clone, it never runs until you approve it.

Quick start

  1. /tools init creates .momo/tools/ with a guide for writing tools (README.md) and an empty requirements.txt.
  2. Write .momo/tools/<name>.py yourself, or let an agent write it: /load-skill workspace-tools, then ask momo in coding mode.
  3. /tools check validates the file without running it.
  4. Read the file, then /tools approve <name>. The model can use the tool from the next message on.
  5. Commit .momo/tools/ and .momo/tools.json. Teammates approve the tools once on their own machines.

run takes exactly the parameters as keyword arguments (give optional ones defaults), plus workdir: the project folder, which is also the current directory. It returns a string, which is all the model sees. The environment has MOMO_WORKDIR, MOMO_TOOL and MOMO_SCRATCH (the scratchpad, for temporary files). No stdin is connected. Anything the tool prints goes to a log, not to the model. An exception, a non-string result or a missing package comes back to the model as an ERROR: it can act on. A good tool also returns its own ERROR: … for expected failures, and says what to do instead.

Approval

  • What you approve. A fingerprint of the workdir, the tool's name, every .py file in .momo/tools/ (a tool may import _helper.py files) and the Python it runs with. /tools approve shows the file, its category, its roles and that Python first.
  • Where it is kept. In ~/.momo-harness/workspace-tools-approved.json, never in the repository, so a repo can't approve its own tools. The same repository cloned somewhere else asks again.
  • When it asks again. After any edit to a file in .momo/tools/ or a change of interpreter: every tool there is back to waiting, and /tools approve all re-approves them in one go. Each call checks the fingerprint again before it runs, and runs exactly the source that was approved.
  • Denied tools stay quiet. approve all skips them; name one to allow it after all.

Dependencies

  1. List the packages in .momo/tools/requirements.txt (pip format) and commit it.
  2. /tools venv creates .momo/tools/.venv with Python's own venv and installs them. It asks first, because installing a package runs its setup code, and pip's output streams into the chat. /tools venv update installs again after the list changed.
  3. The tools now run with that Python, so approve them again.

The interpreter is chosen in this order: "python" in tools.json (e.g. the project's own .venv/bin/python), then .momo/tools/.venv, then momo's own Python, which has no extra packages. A Python inside the workspace came with the repository, so momo only accepts a real virtualenv: a pyvenv.cfg next to it, and an executable that links to a Python outside the workspace. A committed script named python is refused, never run. The virtualenv is not committed, and every machine builds its own.

What runs where

  • Every call is a fresh python -I -B process, started in the project folder. -I leaves momo's code, the current directory, PYTHONPATH and your user site-packages off the import path, so a tool can't import momo. -B writes no __pycache__.
  • A crash or a hang can't take momo down. Esc and the timeout kill the tool and everything it started, and so does output beyond 64 MB.
  • Not a sandbox. The process has your permissions. "Only the workspace's files" is the rule tools are written to, and the guide makes agents follow it, but momo doesn't enforce it. That is why approval is the gate.

Git and the index

.momo/.gitignore lets tools/ and tools.json through and keeps everything else out: the scratchpad, command logs, the plan file, tools/.venv/ and __pycache__/. The .gitignore itself stays out of git, so momo never adds a tracked file you didn't ask for. The code index never contains .momo/, and project-wide searches skip it; the model can still read a tool file by its path.

Editing files

A small model copies old_string with slips, edits without seeing the result, makes one edit per turn and forgets the other places a change has to reach. The edit tools are built around that:

  • They show the result: the changed lines with three lines of context, their new line numbers and the definition they're in. An edit that changes nothing says No change.
  • They catch broken syntax: if the file parsed before the edit and doesn't after, the result names the line, also when an attempted fix left the error in place. The edit stays written, so a change made in two steps still works.
  • They find what the model meant: old_string still matches when only indentation, spacing, quote style or the number of lines differs, and lines the edit keeps are copied from the file, not the model. Ambiguous text is refused rather than guessed, and a miss shows the closest block of the file.
  • They point at what else must change: after a definition is removed, renamed or given new parameters, the result lists the uses still left, from the code index or a bounded scan of the project.
  • They batch: edit_files takes every edit of a change in one call, so a signature change with five callers is one model turn instead of five.

Measured on Qwen3.5-9B with six change requests checked by hidden tests: about 40% fewer tool calls than the same tools with these features off, fewer edit errors and rewrites, and the same pass rate. The failures left are the model's own logic.

Eval details

--suite edit, three runs each. Tool calls went from 289 to 172 with the index off and from 160 to 89 with it on. Edit errors, whole-file rewrites and re-reads of an edited file dropped. edit_files alone cut model turns by 19% (index off) and 27% (index on). Without a model, evals/edit_bench.py puts 66 real edits through typical copying slips: 63 come out exactly right (45 before), and none are written to the wrong place.

The leftover-uses scan without the index stops at 1 s or 5,000 files and says so; a same-named method on another object isn't counted. Syntax is checked by compiling Python and with tree-sitter for other languages.

Command output

A test suite or a build can print tens of kilobytes, even when the model needs one line of it. By default, run_command saves the whole output to a log file and gives the model back only the part it asks for:

  • tail=N: the last N lines. Good for a test summary.
  • grep="regex": the matching lines, numbered. The regex is case-insensitive, context=N adds lines around each match, and with tail=N as well you get the last N matches.
  • Neither: all of it when it fits in 5000 characters. Otherwise its first quarter and last three quarters, cut on line boundaries, with a note of what was left out in between.

stdout and stderr share one log. Every result ends with its path, size and exit code, and when the view hid lines, how many mention an error:

How it's built

The index is built once in the background when momo starts (or on /index on) and then kept current file by file. Every index_* tool reads from memory; only a caller search re-parses the handful of files it needs.

list & skip→parse (tree-sitter)→definitions & imports→identifier occurrences→text signature
  1. List & skip. It walks the tree, keeps what the filter lets in, and skips binary files (the first 4 KB are checked) and files over 2 MB, remembering them so they aren't read again. A first build parses in worker processes (/index-workers, default one less than the CPU count, at most 8), since tree-sitter holds Python's GIL.
  2. Parse. The extension picks a tree-sitter grammar; HTML's inline <script> is parsed as JavaScript at its real line numbers. A file with syntax errors is still indexed but marked incomplete, so a missing hit there isn't taken as proof.
  3. Definitions & imports. code_outline's extractor records each definition's kind, qualified name (Class.method), line range, signature and first docstring line, what a class, interface, trait or object extends or implements, plus the file's imports and their aliases. Imports resolve by each language's own rules: Python's import roots, tsconfig paths and local package names, Rust's crate root, and re-exports through a package's __init__.py or a JS barrel.
  4. Identifier occurrences. One query collects every identifier, stored as 8-byte (file, line) pairs. Whether a use is a call, definition, import or type is worked out only when asked, and only in the files that contain the name.
  5. Text signature. Each file's set of three-letter sequences lets index_text open only the files that could contain the query.

Imports are matched only within a language family (JavaScript/TypeScript/TSX/HTML, C/C++, Java/Kotlin), so java.util.List never resolves to a util.c. Callers come from syntax, not types. Receiver and scope rules remove the usual false hits (self.x in another class, a local that shares the name), but it isn't a type checker; where it can't be sure, it keeps the hit and labels it.

Context & compaction

A small model only knows what is in its context window, and every request sends the whole conversation again. momo decides what goes into each request, shows you how full it is, and drops the least useful parts before the window runs out.

What each request contains

  • The system prompt: role, environment, guides, skills, a running plan and the tool reference.
  • The tool schemas: this mode's tools as JSON. Compaction can't shrink them; switching off unused tools with /tools does.
  • The conversation: your messages (attachments included), the model's replies, its tool calls and their results.
  • The model's earlier reasoning, only as far as /think-history sends it back. The rest stays in the transcript for you and costs no context.

momo asks the server for the model's full window, and the limit you set (/context) is only the point where compaction starts. By default that is half the window. The other half is room for one reply with its reasoning (up to the reply cap) and for the tool results a single step adds before the next check. Raise it with /context 75%, or set an absolute number with /context 16384 or --context.

On Ollama, the full window goes out as num_ctx with every request, and Ollama reserves memory for all of it. A model with a very large native window can need much more RAM or VRAM than its weights alone. On llama.cpp the window is whatever -c set when the server started.

Measuring it

  • The CTX meter in both UIs shows how full the context is against the limit. It turns yellow at 75% and red at 90%. Before a reply the figure is an estimate (about 4 characters per token); after it, the server's own count replaces it.
  • The breakdown, from /context or by clicking the web UI's CTX meter, splits it by category, from system prompt to tool results and reasoning sent back.
  • Big results are kept in check before they arrive. read_file returns at most what the context has free, less 10% of the window. run_command returns a view of its log, fetch_url pages its text by /net-max-chars, and index_map fits a token budget. /tool-result <n> caps every other result too.

Compaction

Before every model call, including each step of a tool loop, momo checks the size of the request. When it's over the limit, momo cuts it down to the system prompt plus a third of the remaining limit, so the next few steps have room before it has to compact again. It works through these steps and stops as soon as the request is small enough:

  1. Stop sending back earlier reasoning (only with /think-history all). It stays in the transcript.
  2. Drop old tool calls, oldest first. Each call goes together with its results and its reasoning. Your questions and the model's answers stay, so the thread of the conversation survives.
  3. Drop whole old turns, oldest first.
  4. Trim the largest tool results that are left to their first two thirds and last third, with a [… N chars removed by context compaction …] marker in between.

Never dropped: the system prompt, so guides, skills and a running plan survive; the question being worked on; and its latest tool calls and results. A model that loses the result it just asked for asks for it again.

The summary. One extra model call (thinking off) summarises what was dropped, keeping decisions, file names, code entities and outcomes, and places it at the top of the oldest remaining message as [Earlier context summary: …]. The next compaction folds it into the new one, so there's only ever one. Nothing changes until the summary is in, so Esc leaves the history intact. /fast-compact skips the summary.

A line in the chat reports each compaction, with the size before and after: Context compacted: summarised 14 messages, trimmed 1 tool result (was ~68,210 tokens, now ~24,880 tokens). /compact runs one by hand.

  • The model forgets earlier work? Raise the limit with /context 75% if the machine has the memory, or do long jobs in plan mode, whose plan lives in the system prompt.
  • Starting something unrelated? /new is better than letting compaction summarise the old task into the new one.
  • "Context not compacted: the system prompt and tool reference alone are …" means the limit is too small for the fixed part. Raise it, or switch off tools, skills or guides.

Thinking & reply length

Three settings shape how a reasoning model works: how much it thinks, how long one reply may run, and whether it sees its own earlier reasoning. All three are remembered between runs and sit under the web UI's THINK badge.

Thinking level

/think off|on|low|medium|high|xhigh (or --think) sets how much the model reasons before it answers. Models take different levels (see the table below), so momo asks the server which ones this model takes and sends only those. It checks again at every message and on /think, because a llama.cpp server may have been relaunched with another model.

  • The nearest level is sent when the model doesn't take yours, and momo says so (THINK: high→xhigh, or high→on on an on/off model). Your choice is kept, so a model that takes it gets it.
  • on sends no level, so the model uses its own default. A model without thinking gets nothing (badge: THINK: n/a).
  • No separate reasoning budget: llama.cpp's --reasoning-budget is fixed when the server starts, and Ollama has none. The reply cap bounds reasoning and answer together.

Compaction summaries, companion recaps and the retry after a cut-off reply always ask for no reasoning.

Reply cap

Every request limits how long one reply may be, reasoning included: /max-output-tokens, default 25,000 tokens (max_tokens on llama.cpp, num_predict on Ollama).

  • Why: a model caught in a repetition loop otherwise runs until the context is full; in one eval, a reply ran to 125,000 tokens and 80 minutes.
  • At the cap: if the reply was cut off before it said anything or called a tool (usually the reasoning used it all), momo asks once more with thinking off and says so: "Response cut off … Retrying without thinking."
  • Setting it: /max-output-tokens 30000, off for no cap (minimum 256), --max-output-tokens, or View → Context → Reply cap.

Sending reasoning back

/think-history off|turn|all decides whether the model sees its own earlier reasoning. turn (the default) sends it back for the current tool loop, since your last message. all also sends earlier turns, and off sends none. It is remembered, and in the web UI it is under the THINK menu.

  • Why: models are trained to see their reasoning from the earlier steps of a tool loop. With off, the model sees its earlier tool calls without the reasoning behind them, and tends to plan again from scratch after every result.
  • Cost: sent reasoning counts toward the context (Reasoning sent back in the CTX breakdown). With all, compaction stops sending earlier turns' reasoning before it removes any messages.

Measured with the code-navigation evals on Qwen3.5-9B: turn was as accurate as off, made a quarter fewer tool calls and took about 40% less time. all hasn't been measured.

Internet access

fetch_url and web_search are the only tools that reach anything but your model server, so they're off by default: the model isn't offered them until you turn them on, and they switch off again at every launch. Everything below applies to both.

momo

While it's on, the system prompt tells the model to check versions and APIs rather than recall them, read the project's manifests first, stop once answered, and cite URLs.

What is blocked

  • Any scheme except http and https. The client is built without urllib's file, ftp and data handlers.
  • Loopback, private, CGNAT and link-local addresses, unless you use /net local. Every resolved address is checked, so http://2130706433/ and http://127.1/ are blocked too.
  • Redirects into blocked addresses, because every hop is re-checked. When a redirect changes the scheme, host or port, every header the model set is dropped except Accept, Accept-Language, User-Agent and Content-Type, since a token can hide under any name.
  • DNS rebinding: the connection is pinned to the exact addresses that were checked, so a resolver can't answer "public" for the check and 169.254.169.254 a moment later. Certificates are still validated against the hostname.
  • Credentials in the URL, control characters in URLs and responses, and compressed bodies (so no gzip bombs).
  • Writes to local or private addresses always ask for confirmation, even with /net-confirm off.

Prompt injection and exfiltration aren't solved. Fetched pages are fenced as untrusted content, but small models don't resist injection well. Turn on /run-confirm on while browsing, and keep an eye on the URLs in the transcript.

MCP servers

momo is a Model Context Protocol client. Add a server and its tools become tools the model can call, next to momo's own. It speaks both transports, a local command over stdio and a remote streamable HTTP endpoint, and like the rest of momo it needs no packages.

Servers live in the common mcpServers format (the same as Claude Desktop and Claude Code), in two files:

Servers start in the background, so momo never waits for one at launch; your first message waits up to 10 seconds for any still starting (an npx or uvx server downloads itself the first time). A server that crashes after it worked is restarted with backoff, up to five times.

An MCP server is code you chose to run, with your permissions, and a remote one sees whatever the model sends it. momo keeps its side tidy: plain http:// only to this machine or the LAN, no redirects (so a token can't be passed on), control characters stripped from everything a server sends, and its stderr kept in ~/.momo-harness/mcp-logs/ rather than on your screen. Review a server's tool descriptions with /mcp tools: they go into the prompt. Not supported yet: OAuth, MCP prompts, sampling and elicitation, the legacy SSE transport, and image results.

What protects it

  • Loopback by default. momo binds to 127.0.0.1 and rejects any request whose Host isn't a loopback name, so a website can't reach it by pointing its own domain at your machine (DNS rebinding).
  • Same-origin writes. Anything that changes state must be a JSON request from the page itself.
  • A token off loopback. On any other address, every request needs the access token, which is never written to disk. HTTPS, when on, encrypts it but never replaces it.
  • No-token mode keeps the Host check. --web-insecure prints a warning, and accepts only this machine's own names and addresses (plus any you add with --web-allow-host), so a website you visit still can't drive momo. Anyone who can reach the address can, so use it only where you trust every device.

The access token

There's no login form. The token is part of the web UI URL momo prints at startup, in the TUI's chat pane or, with --headless, the terminal: Web UI: http://my-mac.local:8765/?token=Xq3… (with 0.0.0.0, the hostname replaces the address). No command shows it again; scroll back, restart momo, or set --web-token.

  • In a browser: open the full URL once. momo swaps the token for a cookie (momo_token, HttpOnly, SameSite=Strict) and redirects to /, so the token leaves the address bar and history. Bookmark the plain address. If the hostname doesn't resolve on the other device (it relies on .local/mDNS or your DNS), use the IP address and keep the token.
  • From scripts: send it as a header on every request: curl -H "Authorization: Bearer $TOKEN" http://my-mac.local:8765/api/state. See HTTP API.

Behind a reverse proxy

Keep momo on loopback with a fixed token; token mode lets the proxy pass its own Host header:

bash
python momo-coding-harness.py --web-host 127.0.0.1 --web-token "$(openssl rand -hex 16)"
Caddyfile
momo.example.com {
    reverse_proxy 127.0.0.1:8765
}
nginx
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_set_header Host $host;   # the Origin check compares against it
    proxy_buffering off;           # /api/events is Server-Sent Events
    proxy_read_timeout 1h;
}

Then open https://momo.example.com/?token=<token> once. Never let the proxy strip the Origin header: a missing Origin passes the same-origin check, so any website could then send commands to momo.

Keep it safe

  • Treat the token like a password: anyone with it controls momo, and it sits in your terminal scrollback.
  • Over plain HTTP the token and cookie are visible on the network. Use HTTPS on anything but a network you trust.
  • Turn on /run-confirm on when others can reach the UI, or when browsing with /net on, so no shell command runs unseen.

Sessions

A session is saved after every reply: the messages, mode, model, host, workdir, context settings, active skills, per-mode tool choices, plan and input history. The next launch restores the last one (--fresh skips that). The tokens are the one thing left out.

  • /sessions lists recent sessions with their mode and model; /session <name> loads one by name or prefix.
  • In the web UI, the session drawer (clock icon) loads, starts and deletes sessions: hover a row for its trash button, or use Select to delete several at once. The open session is always kept.

Elsewhere

  • In your project: .momo/plan.md while a plan exists (deleted when it completes or is cancelled), and conversation-<timestamp>.md when you run /export.
  • In each browser: the web UI keeps its theme, view options and notification switches in localStorage; the token cookie lasts until the browser closes.
  • Never stored: the model server token (/token) and the web UI access token.

Keep ~/.momo-harness/ private: sessions and logs contain your conversations, tool output from your code, and the paths of your projects. To start completely fresh, quit momo and delete the folder.

Tests & evals

bash
python -m unittest discover tests                 # do the tools work?
python evals/run_evals.py --runs 3                # does the model use them? (needs a server)

tests/ uses the standard-library unittest. It includes one fixture per tree-sitter grammar, so a grammar upgrade that renames a node fails a test instead of silently emptying a tool's output. evals/ asks questions with known answers and scores whether the model reached the right tool, how many calls it took and how much output it pulled into context. --suite shell --run-mode new|classic compares the two ways run_command returns output. Sampling isn't pinned, so read the min–max spread, not a single run.

bash
python evals/edit_bench.py                        # edit_file's matcher, no model
python evals/run_evals.py --suite edit            # change requests, checked by running them
python evals/replay.py --exp R2 --n 10            # one tool result, two wordings, same conversation

edit_bench.py puts real edits through the slips a model makes when it copies old_string and counts how many land exactly right; a unit test keeps wrong-place writes at zero. --suite edit asks the model for six changes on a small project, checks each with hidden tests, and counts edit errors, re-reads and turns (--edit-features switches the edit extras off for an A/B). replay.py replays a real session up to one tool result and lets the model continue with that result worded two ways, which isolates the effect of a single message.
