A coding assistant that stays on your machine.

momo connects to an Ollama or llama.cpp server and gives the model tools to read, search, edit and run your project. Use it from a terminal UI, a browser, or both. It needs only the Python standard library, uses about 40 MB of RAM, and talks only to the model server you choose (plus any MCP servers you add). A small black cat keeps you company.

Getting started

Requirements

  • macOS or Linux. On Windows, use WSL (the terminal UI needs curses).
  • Python 3.14+. No packages are required; requirements.txt only adds features.
  • A model server: Ollama, or llama.cpp's llama-server (older builds need --jinja for tool calls).
  • A model that can call tools. A 9B model such as qwen3.5:9b with a 32k+ context window is a good start. Bigger models (qwen3-coder:30b) handle multi-step tasks better.

Install

bash
git clone https://github.com/bameschot/momo-coding-harness.git
cd momo-coding-harness
python3.14 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Run

bash
python momo-coding-harness.py                     # TUI + web UI on 127.0.0.1:8765

# a specific project on a remote Ollama
python momo-coding-harness.py --workdir ~/projects/myapp \
    --model qwen3-coder:30b --host http://192.168.1.10:11434

# a local llama.cpp server
python momo-coding-harness.py --provider llamacpp --host http://localhost:8080

The provider and host are remembered. See Running against a backend for setups and Command-line flags for every option.

The web UI only listens on this machine by default. To open it from a phone or another computer, see Access & security, and set up HTTPS & certificates.

Your first session

  1. Check the startup line. It shows the model, its context window and the web UI address. offline means momo can't reach the server: check --host.
  2. Describe what you want. momo starts in design mode, which reads code and asks questions but doesn't change it.
  3. Switch mode to act on it. Shift+Tab or /code for a direct change, /plan to plan it first. See Modes.
  4. Pick it up later. The next launch restores your session. --fresh or /new starts over.

Remote servers

Your files and tools stay on the machine running momo, but every request sends the server your messages and whatever the model has read or run. Use a server you trust with your code.

  • Give the full URL, including http:// or https://.
  • Prefer an SSH tunnel to exposing the model port: ssh -L 11434:127.0.0.1:11434 gpu-box, then use the default host. HTTP_PROXY is not used, so a tunnel is also how to go through a jump host.
  • Use HTTPS on untrusted networks, especially if you send a token.

When it doesn't connect

  • Server down? The status bar shows offline. momo checks again before every message, so just restart the server.
  • No context window detected? Set one with --context 16384.

How momo works

You send a message. momo passes it to the model with a system prompt (instructions for the current mode) and the tools the model may call. When the model asks for a tool, momo runs it in your working directory and sends the result back. This repeats until the model answers in text.

  • Modes decide which tools are offered. See Modes.
  • Context is everything sent in one request. See Context & compaction.
  • "momo" is the app, one of its modes and the cat.

Cycle with Shift+Tab, or switch with /design, /chat, /plan, /code or /momo.

Plan mode

momo investigates, writes a step-by-step plan to .momo/plan.md, and changes nothing until you approve it. There are two kinds:

  • Normal (/plan, the default): the model says when each step is done.
  • Test-driven (/plan tdd): tests are written first, and momo runs them to check each step. See Test-driven plans.
  • Before approving, you can edit .momo/plan.md by hand: reword, reorder, add or delete steps, or mark one [-] to skip it.
  • Approving switches to coding mode and runs the plan one step at a time. The plan stays in the system prompt, so the model keeps its place.
  • A paused plan carries on with /plan resume or any message, even after a restart.
CommandEffect
/planSwitch to plan mode, showing the current plan's state if there is one
/plan tdd · /plan normalChoose a test-driven or a normal plan
/plan showThe plan with the status of each step
/plan runApprove a kept plan and execute it (re-reads the file)
/plan resumeContinue a paused plan from its current step
/plan cancelDiscard the plan and delete .momo/plan.md

Test-driven plans

A normal plan trusts the model to say when a step is done. A test-driven plan checks. First, the expected outcomes of every step become tests, all skipped so the build stays green. Each step then switches its own tests on and must make them pass. momo runs the suite itself to confirm.

What the plan holds

  • test_command: runs the whole suite, e.g. python -m pytest -q.
  • tests per step: outcomes written as action → expected result, e.g. remove("apple", 3) when 2 are in stock → ValueError.
  • acceptance: the outcomes of the whole change.
  • Optional step_test_command for slow suites. See Slow suites.

Each step gets a fixed tag (tdd-step-1, tdd-step-2 …, plus tdd-acceptance) that links it to its tests.

Skip markers

Pending tests use the test framework's own skip, on its own line directly above a complete test, with the tag in the reason:

FrameworkMarker
Python unittest@unittest.skip("tdd-step-2")
pytest@pytest.mark.skip(reason="tdd-step-2")
JUnit@Disabled("tdd-step-2")
Rust#[ignore = "tdd-step-2"]
Got.Skip("tdd-step-2") as the first line of a complete test
Jest, Vitest, Mochait.skip("adds (tdd-step-2)", …)

When a step starts, momo removes the markers with its tag. In compiled languages the model may add stubs so skipped tests still compile.

What the gate checks

StageBefore the suite runs
Writing the testsEvery tag appears in the project, and no test is empty.
A stepThis step's and earlier steps' tags are gone, no check was deleted, and finished steps' tests are unchanged.
AcceptanceNo tdd- tag is left anywhere.

Then test_command must pass. Approving the plan also approves running that command after every step.

  • Test changes are audited. Deleting a check, or changing a finished step's test, is refused. Other test changes are listed in the chat.
  • Three failures ask you. If a step fails its gate three times, momo asks you for guidance, or pause to stop.
  • Tests that already pass are reported to the model, which either finishes the step or tightens the tests.

Slow suites

  • step_test_command runs only the step's own tests for the red check, e.g. python -m pytest -q {files} or go test {dirs}. The full suite remains the gate.
  • The model's own run counts. If the model just ran test_command, it passed and nothing changed since, momo doesn't run it again.

Skills & project guides

Skills are Markdown files in skills/ that are added to the system prompt. You can load several, and they stay loaded across mode switches.

momo

/load-skill python

In the web UI, the book button lists every skill with a checkbox. Built-in skills cover languages (python, rust, java, sql …) and tasks (code-review, tdd, software-design …). To add your own, drop a .md file into the folder.

Project guides (/guides on) load the project's AGENTS.md, CLAUDE.md, MOMO.md, GEMINI.md, .github/copilot-instructions.md or .cursorrules into the system prompt.

The companion

momo is the ASCII cat walking along the input box. It mews lines that fit the current mode. Shift+Q or /companion off hides it. With /companion-idle-recap on, it recaps what you just did when you've been idle for a while.

Turning tools on and off per mode

Each mode keeps its own choices. A tool you turn off is hidden from the model.

momo
/tools                     # pick this mode's tools: TUI checklist, web Tools menu
/tools list                # grouped, ✓ on / ✗ off
/tools run_command         # what it does, its parameters, whether it's on
/tools run_command off     # one or more names, then on|off
/tools off                 # all tool calls off, as before
  • TUI: /tools opens a checklist (Space toggles). Web UI: the wrench button.
  • Choices are saved with the session; /new starts with every tool on.
  • Plan mode's own tools can't be switched off.

How tools are built

Every tool is one Python file that holds everything about it: the function that runs, the schema the model sees, and when it is offered. Adding a tool means adding a file, for built-in tools and your own alike.

Anatomy of a tool file

A shortened built-in tool, delete_file.py:

harness/tools/builtin/delete_file.py
"""delete_file: remove one file (never a folder)."""
from pathlib import Path

from ...paths import safe_entry_path
from ..registry import Tool, tool_schema


# 1. The function: the model's arguments, plus workdir; returns the text the model gets back.
def delete_file(path: str, *, workdir: Path) -> str:
    p = safe_entry_path(path, workdir)          # an ERROR string when the path leaves the workdir
    if isinstance(p, str):
        return p
    ...
    return "OK"


TOOL = Tool(
    # 2. The schema: exactly what the model sees.
    tool_schema("delete_file",
        "Permanently delete a single file (this cannot be undone). ...",
        {"path": {"type": "string", "description": "File to delete"}},
        ["path"]),
    # 3. How momo offers it and treats a call.
    run=delete_file,
    order=470,                  # its place in every tool list
    group="edit & shell",       # its section in the /tools pickers
    writes=("path",),           # re-index this path after the call
    diff=True,                  # the frontends show what changed
    example={"path": "old-file.py"})   # the example call in the tool reference

The description matters most: it is all the model knows about the tool.

Your own tools

Put a tool file in ~/.momo-harness/tools/ and run /tools reload. It appears under "custom" and works like any other tool. A complete example, docs/examples/tools/word_count.py:

~/.momo-harness/tools/word_count.py
from pathlib import Path
from harness.tools import ALL_ROLES, Tool, read_text, tool_schema

def word_count(path: str, *, workdir: Path) -> str:
    got = read_text(path, workdir, refuse_binary=True)   # stays inside the workdir
    if isinstance(got, str):
        return got                                       # an "ERROR: ..." the model can act on
    _, text = got
    return f"{path}: {len(text.splitlines()):,} lines, {len(text.split()):,} words"

TOOL = Tool(
    tool_schema("word_count",
                "Count the lines, words and characters of a text file in the project.",
                {"path": {"type": "string", "description": "File to count, e.g. 'README.md'"}},
                ["path"]),
    run=word_count, modes=ALL_ROLES, keeps_green=True, example={"path": "README.md"})
shell
mkdir -p ~/.momo-harness/tools && chmod 700 ~/.momo-harness/tools
cp docs/examples/tools/word_count.py ~/.momo-harness/tools/
chmod 600 ~/.momo-harness/tools/word_count.py
# then in momo:  /tools reload

To ask you something, a tool takes inject=("ctx",) and calls ctx.ask_user(question). With confirm=True, momo asks you before every call.

A custom tool is code that runs inside momo. It is only loaded from ~/.momo-harness/tools/, never from a project, and only when the folder (chmod 700) and file (chmod 600) are yours. A file that fails to load is reported, and momo starts without it.

CommandDescription
/tools reloadLoad ~/.momo-harness/tools/ again
/tools errorsWhy a tool file did not load
/tools <name> offTurn it off for this mode

A project can also ship its own tools for the whole team: see Workspace tools.

Writing a tool a small model uses well

  • Lead with what it is for. A small model chooses tools by the first sentence of the description.
  • Return errors it can act on. Start with ERROR: and say what to do instead.
  • Keep results bounded. Cap long output and say how to get the rest.
  • Hint in the result. Suggest the next useful call in the tool's own output, not in the prompt.
  • Honour Esc. A slow tool takes inject=("cancel",) and stops when cancel.is_set().

Workspace tools

Put tools in .momo/tools/ and commit them, and everyone who opens the project in momo gets them: a report generator, a convention check, a wrapper around project scripts. Unlike your own tools, a workspace tool runs in its own process and never runs until you approve it, because it arrives with a clone.

Quick start

  1. /tools init creates .momo/tools/ with a guide (README.md).
  2. Write .momo/tools/<name>.py, or let momo write it: /load-skill workspace-tools, then ask in coding mode.
  3. /tools check checks the file without running it.
  4. Read the file, then /tools approve <name>.
  5. Commit .momo/tools/ and .momo/tools.json. Teammates approve once on their own machines.

The tool file

.momo/tools/todo_count.py

                   "most first.",
    "parameters": {
        "path": {"type": "string", "description": "Folder or file to scan (default: the whole project)"},
        "limit": {"type": "integer", "description": "Files to list (default 20)"},

    "required": [],

    "timeout": 60,

    root = (workdir / path).resolve()
    if root != workdir.resolve() and workdir.resolve() not in root.parents:
        return f"ERROR: {path} is outside the project — pass a path inside it, e.g. 'src'"

Dependencies

  1. List packages in .momo/tools/requirements.txt and commit it.
  2. /tools venv creates .momo/tools/.venv and installs them (it asks first). /tools venv update reinstalls.
  3. Approve the tools again, since their Python changed.

To use the project's own virtualenv instead, set "python" in tools.json. Without either, tools run with momo's Python. momo only accepts a real virtualenv, never a committed script named python.

What runs where

  • Every call is a fresh Python process in the project folder. It can't import momo, and a crash or hang can't take momo down. Esc and the timeout kill it.
  • Not a sandbox. The tool has your permissions. That is why approval is required.

Only tools/ and tools.json in .momo/ are meant for git; momo's .momo/.gitignore keeps the rest out.

Editing files

Small models make copying slips, edit blind and forget related places. The edit tools help with that:

  • They show the result: the changed lines with context and their new line numbers.
  • They catch broken syntax and name the line.
  • They forgive small slips: old_string still matches when only indentation, spacing or quotes differ. Ambiguous matches are refused, not guessed.
  • They point at what else must change: after a rename or signature change, the result lists the remaining uses.
  • They batch: edit_files makes every edit of a change in one call.

Command output

Builds and test suites print a lot, but the model usually needs a few lines. run_command saves the full output to a log and returns only what the model asks for:

  • tail=N: the last N lines.

  • Neither: everything if it is short, otherwise the start and end with a note of what was left out.

Context & compaction

The model only knows what is in its context window, and every request sends the whole conversation again. momo shows how full it is and drops the least useful parts before it runs out.

What each request contains

  • The system prompt, including skills, guides and a running plan.
  • The tool schemas. Switching off unused tools with /tools saves room.
  • The conversation: messages, attachments, tool calls and results.
  • The model's earlier reasoning, as far as /think-history sends it back.

The limit (/context) is where compaction starts: by default half the window, leaving the other half for the reply. Raise it with /context 75% or set tokens with /context 16384.

On Ollama, memory is reserved for the model's full window. A model with a very large window can need much more RAM or VRAM than its weights alone.

Measuring it

The CTX meter shows how full the context is. It turns yellow at 75% and red at 90%. /context, or clicking the meter in the web UI, breaks it down by category. Large tool results are capped before they arrive.

Compaction

Before every model call, momo checks the request size. When it's over the limit, momo removes, in order, until it fits:

  1. Earlier reasoning (only with /think-history all).
  2. Old tool calls and their results, oldest first. Your questions and the model's answers stay.
  3. Whole old turns, oldest first.
  4. The middle of the largest remaining tool results.

The system prompt, the current question and its latest tool results are never dropped. One extra model call summarises what was removed and keeps it at the top of the conversation. /fast-compact skips the summary; /compact compacts by hand.

  • The model forgets earlier work? Raise the limit, or use plan mode for long jobs: the plan stays in the system prompt.
  • Starting something unrelated? Use /new.
  • "Context not compacted" means the limit is too small for the system prompt and tools alone. Raise it, or switch off tools, skills or guides.

Thinking & reply length

Three settings shape how a reasoning model works: how much it thinks, how long a reply may be, and how much of its earlier reasoning it sees. All are remembered and sit under the web UI's THINK badge.

Thinking level

/think off|on|low|medium|high|xhigh (or --think) sets how much the model reasons. If the model doesn't support your level, momo sends the nearest one and shows it (THINK: high→xhigh). on uses the model's own default.

Reply cap

/max-output-tokens limits one reply, reasoning included. The default is 25,000 tokens; off removes the cap.

  • Why: a model stuck in a repetition loop would otherwise run until the context is full.
  • At the cap: if the reasoning used up the whole reply, momo retries once with thinking off.

Sending reasoning back

/think-history off|turn|all decides whether the model sees its own earlier reasoning. turn (default) sends it back since your last message, all also for earlier turns, off never. Without it, the model tends to re-plan from scratch after every tool result. Sent reasoning does use context.

Trimming what is sent back

/think-keep off|lean|more|most decides how much of that reasoning goes back. The model mainly needs to know where it got to, so lean sends just its plan steps and closing sentences. Code is never cut, and your transcript keeps everything.

commands
/think-keep lean  # plan steps and closing sentences (the default)
/think-keep more  # twice as much; most: four times
/think-keep off   # send it back whole

lean suits small models; more or most give a larger model more of its own thinking.

Cavecat mode

A nod to caveman, which makes a model talk like a caveman to save tokens. momo is a cat, so: cavecat. On a local model, output tokens cost time, so /cavecat on cuts the text a turn produces:

  • Short replies: the result first, then what changed and what you must decide.
  • No narration between tool calls.
  • Terse plans and tool text: plan steps, questions and commit messages as "verb + file + change".
  • Compacted command output: long runs of passing or repeated lines fold into one note. Error and warning lines always stay.

Code, paths, error text and numbers are never compressed, and thinking is left alone: compressing it made the model work worse. momo mode keeps its own voice.

commands
/cavecat on       # or --cavecat on at startup
/cavecat off      # the default

Internet access

fetch_url and web_search are the only tools that reach beyond your model server, so they are off by default and switch off again at every launch.

momo
/net on | local | off     # public only · also localhost + LAN · blocked
/net-confirm on|off       # ask before POST/PUT/PATCH/DELETE (default on)
/net-max-bytes 2mb        # download cap
/net-max-chars 24000      # text returned per call; the rest is paged

What is blocked

  • Any scheme except http and https.
  • Local and private addresses, unless you use /net local. Every resolved address is checked, including after each redirect.
  • Headers the model set are dropped when a redirect goes to another site.
  • Credentials in URLs and compressed responses.
  • Writes to local or private addresses always ask first.

Fetched pages are marked as untrusted, but small models don't resist prompt injection well. Turn on /run-confirm on while browsing, and watch the URLs in the transcript.

MCP servers

Add a Model Context Protocol server and its tools join momo's own. Both local (stdio) and remote (HTTP) servers work.

Adding a server

Servers use the common mcpServers format (as in Claude Desktop and Claude Code), in two places:

  • ~/.momo-harness/mcp.json: your own servers. /mcp add writes here.
  • <workdir>/.mcp.json: a project's servers. These only start after you approve them with /mcp approve <name>.
~/.momo-harness/mcp.json
{"mcpServers": {
  "git":    {"command": "uvx", "args": ["mcp-server-git", "--repository", "."]},
  "github": {"type": "http", "url": "https://api.githubcopilot.com/mcp/",
             "headers": {"Authorization": "Bearer ${GITHUB_TOKEN}"},
             "confirm": "always", "tools": {"include": ["get_*", "list_*"]}}
}}

${VAR} is read from your environment, so tokens stay out of the file. momo adds a few keys of its own:

KeyDefaultDescription
confirmwritesWhen to ask before a call: always, writes (unless the server marks the tool read-only) or never
toolsall{"include": [...], "exclude": [...]}: which of the server's tools to offer
timeout120Seconds per call
untrustedon for HTTPFence results as untrusted content, like fetch_url
enabledtruefalse keeps the server configured but stopped

What the model sees

  • Tools are named mcp__<server>__<tool>.
  • Read-only modes only get the tools a server marks read-only.
  • Every MCP tool can be turned off per mode in the tool picker. Large servers cost context, so offer only the tools you need.

Confirming calls

By default, a tool that isn't marked read-only asks before it runs. Answer y, n, or a to always allow that tool this session.

Managing servers

In the web UI, the plug button opens an overview of every server and its tools. In the TUI, /mcp opens a server picker. Or use the commands:

momo
/mcp list                          # servers, state, tool counts
/mcp add git uvx mcp-server-git    # a stdio server (--env K=V before the command)
/mcp add web --http https://h/mcp  # an HTTP server (--header K=V after the URL)
/mcp tools git                     # what the model sees, with descriptions
/mcp approve|deny <server>         # project servers
/mcp restart|enable|disable <server>
/mcp log <server>                  # the server's stderr
/mcp resources [server]            # and /mcp read <server> <uri>
/mcp reload                        # re-read both files; only changed servers restart
/mcp on|off                        # all MCP servers (remembered)

An MCP server is code that runs with your permissions, and a remote one sees whatever the model sends it. Check a server's tool descriptions with /mcp tools: they go into the prompt. Not supported yet: OAuth, MCP prompts, sampling, the legacy SSE transport and image results.

What protects it

  • Loopback by default, and requests for other host names are rejected, so a website can't reach momo through your browser.
  • Changes must come from the page itself, not another site.
  • A token on any other address. HTTPS encrypts it but never replaces it.
  • --web-insecure drops the token but keeps the host check. Anyone who can reach the address controls momo, so use it only on a network you fully trust.

The access token

The token is part of the web UI address momo prints at startup: Web UI: http://my-mac.local:8765/?token=Xq3….

  • In a browser: open that full URL once. momo swaps the token for a cookie, so afterwards you can bookmark the plain address. If the hostname doesn't resolve, use the IP address.
  • From scripts: send Authorization: Bearer $TOKEN. See HTTP API.

HTTPS

Use HTTPS whenever other devices reach the web UI: it encrypts the token, and makes notifications and copy buttons work there. --web-tls auto is the easiest way. See HTTPS & certificates for setup, your own or a self-signed certificate, and reverse proxies.

Keep it safe

  • Treat the token like a password: anyone with it controls momo.
  • Use HTTPS on any network you don't fully trust.
  • Turn on /run-confirm on when others can reach the UI or the internet tools are on.

Reaching momo by another name, such as a VPN address? Add it with --web-tls-name. Repeat it for each DNS name or IP address:

bash
python momo-coding-harness.py --web-host 0.0.0.0 --web-tls auto \
    --web-tls-name my-mac.tailnet.ts.net --web-tls-name 100.101.102.103

Trusting the CA on a device

  1. Get the CA certificate. Open https://<host>:8765/momo-ca.pem on the device (no token needed, it is public), or copy ~/.momo-harness/tls/momo-ca.pem over.
  2. Check its fingerprint against the SHA-256 momo printed at startup. On a computer: openssl x509 -in momo-ca.pem -noout -fingerprint -sha256.
  3. Install it as a trusted root:
    DeviceHow
    macOSOpen it in Keychain Access, then set When using this certificate to Always Trust
    iOS / iPadOSInstall the downloaded profile, then enable it under Settings → General → About → Certificate Trust Settings
    AndroidSettings → Security → Encryption & credentials → Install a certificate → CA certificate
    LinuxCopy it to /usr/local/share/ca-certificates/momo-ca.crt and run sudo update-ca-certificates
    FirefoxHas its own store: Settings → Privacy & Security → Certificates → View Certificates → Import
    WindowsOpen it and install it into Trusted Root Certification Authorities
  4. Open the printed URL. Without these steps the connection is still encrypted, but the browser shows a warning.

Renewal

The server certificate lasts 397 days, the most browsers accept. momo issues a new one 30 days before it expires, and whenever your hostname or IP address changes. Devices that trust the CA don't need to do anything.

Why the CA is safe to trust

The CA can only vouch for local names and private addresses: localhost, *.local, your hostname, private and loopback ranges, Tailscale's 100.64.0.0/10, and names you gave with --web-tls-name when it was created. Even if momo-ca.key leaked, it couldn't fake a public website. Still, never share that key.

Because of this, a name you add later must fit those rules. A public name or address won't fit; momo then refuses to start the web UI. Either start over with a new CA (below), or use your own certificate.

Starting over

Quit momo and delete ~/.momo-harness/tls/. The next start with --web-tls auto creates a new CA, and every device must trust the new one.

~/.momo-harness/tls/
tls/                  # folder 0700, keys 0600; refused if not yours
├── momo-ca.pem       # the CA certificate you trust on your devices
├── momo-ca.key       # the CA's private key: never share
├── momo-ca.json      # the names the CA may vouch for
├── server.pem        # this machine's HTTPS certificate
├── server.key
└── server.json       # the names it covers, and its expiry

Your own certificate

bash
python momo-coding-harness.py --web-host 0.0.0.0 \
    --web-cert my-mac.pem --web-key my-mac-key.pem
  • PEM format. If the certificate needs intermediate certificates, put them in the same file, after it.
  • It must name the address you browse to, in its Subject Alternative Names: the hostname, IP, or both.
  • The key must not have a password. Leave out --web-key if the key is inside the certificate file.
  • You handle renewal. Replace the files and restart momo.

A certificate that can't be loaded stops the web UI at startup with Web UI failed to start … (with --headless, momo exits). --web-cert can't be combined with --web-tls auto.

Making a self-signed certificate

If you'd rather not use momo's CA, you can make a single self-signed certificate with openssl. Replace the names and IP with the ones you use:

bash
openssl req -x509 -newkey rsa:2048 -nodes -days 397 \
    -keyout momo-key.pem -out momo.pem -subj "/CN=my-mac.local" \
    -addext "subjectAltName=DNS:my-mac.local,DNS:localhost,IP:192.168.1.20"

python momo-coding-harness.py --web-host 0.0.0.0 --web-cert momo.pem --web-key momo-key.pem
  • Trust momo.pem on each device, the same way as momo's CA.
  • Keep momo-key.pem private: chmod 600 momo-key.pem.
  • When it expires, or your IP changes, make a new one and trust it again on every device. --web-tls auto does all of this for you, which is why it's usually the better choice. mkcert is another option.

Behind a reverse proxy

For a public domain name, let a proxy such as Caddy or nginx handle HTTPS. Keep momo on loopback with a fixed token:

bash
python momo-coding-harness.py --web-host 127.0.0.1 --web-token "$(openssl rand -hex 16)"
Caddyfile
momo.example.com {
    reverse_proxy 127.0.0.1:8765
}
nginx
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_set_header Host $host;   # the Origin check compares against it
    proxy_buffering off;           # /api/events is Server-Sent Events
    proxy_read_timeout 1h;
}

Then open https://momo.example.com/?token=<token> once.

Never let the proxy strip the Origin header. momo uses it to refuse requests from other websites. Without it, any site you visit could send commands to momo.

Troubleshooting

SymptomFix
The browser warns the connection isn't privateThat device doesn't trust the CA yet. See Trusting the CA.
The warning names a different hostYou browsed to a name the certificate doesn't cover. Add it with --web-tls-name, or use the printed URL.
--web-tls auto needs the openssl commandInstall openssl, or use --web-cert.
momo's CA was created without …The new name doesn't fit the CA's rules. Start over with a new CA, or use your own certificate.
refusing …: it must be owned by youFix the owner or permissions of ~/.momo-harness/tls/.

Where momo stores data

Everything momo keeps lives in ~/.momo-harness/, except per-project files in .momo/. None of it is sent anywhere. Deleting the folder resets momo completely.

Sessions

A session (messages, mode, model, skills, plan and settings) is saved after every reply and restored on the next launch. Tokens are never saved. /sessions lists recent ones and /session <name> loads one; in the web UI, the session drawer also deletes them.

Keep ~/.momo-harness/ private: sessions and logs contain your conversations and output from your code.

Tests & evals

bash
python -m unittest discover tests                 # do the tools work?
python evals/run_evals.py --runs 3                # does the model use them? (needs a server)

The unit tests use the standard-library unittest and need no model. The evals check whether a real model uses the tools well, so they need a running server. Other suites are selected with --suite (e.g. edit, shell, cavecat); see evals/README.md.
