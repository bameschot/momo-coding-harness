A coding assistant that stays on your machine.

momo connects to a local Ollama or llama.cpp server and gives the model tools to read, search, edit and run your project. Use it from a split-pane terminal UI, a browser window, or both at once. It's lightweight: four Python dependencies, no build step, and about 60 MB of RAM. A small black cat keeps you company.

feature overview

What it does

Everything below works offline against a model you run yourself. Each card links to the detailed documentation further down this page.

Ollama or llama.cpp, local or remote

Point momo at an Ollama server (native API, switch models with /model) or a llama.cpp llama-server (OpenAI-compatible API, with Jinja chat templates for tool calling). Either can run on your own machine or a GPU box elsewhere. Pick one with --provider and --host, move between servers with /host, and add a Bearer token with /token; it is never written to disk. Every mode, tool and UI works the same on both.

Backends & setup →

Lightweight by design

momo is a plain Python program with four dependencies: the Ollama client, httpx for llama.cpp, tree-sitter with its grammars, and optionally pypdf. About 35 MB installed. The terminal UI is curses and the web UI is Python's own HTTP server, so there's no Node, no build step, no database and no background daemon. It uses about 60 MB of RAM idle, and 105–150 MB with the code index built for projects of 180 to 2,100 files. The model's memory lives in Ollama or llama.cpp, not in momo.

Terminal UI

A three-pane curses interface: chat, status bar and a multi-line input. Replies stream in, tool calls and thinking are colour-coded, and file edits show as coloured diffs.

Web UI, same session

A browser chat window served by Python's standard library, with no CDN or build step. It shows the same session as the terminal, so you can type in either one.

Design, chat, plan, coding and momo. Each mode has its own role prompt and tool set, from read-only exploration to full edit-and-run.

Plan, approve, execute

Plan mode investigates first and writes a step-by-step plan to .momo-plan.md. Nothing changes until you approve it. Then it runs one step at a time and can pause and resume.

Syntax-aware navigation

Tree-sitter outlines, symbol lookup and references for Python, Java, C/C++, Kotlin, Rust, JS/TS and more, plus config keys, CSS selectors, SQL tables and Dockerfile stages.

Tools →

In-memory code index

On by default. It supports fuzzy definition search, full-text search, callers grouped by function and a ranked project map, and it waits for pending changes before answering so results are never stale.

Guarded internet access

An opt-in fetch_url tool that is off by default. Private addresses are blocked, redirects are re-checked, credentials are dropped across origins and page content is fenced off as untrusted.

Sandboxed by default

Every file operation stays inside the working directory. run_command can ask first, and the web UI binds to loopback and needs a token off-loopback.

Sessions auto-save after every reply. The CTX meter tracks token use, and compaction summarises old history with the model when the limit is reached.

Getting started

Requirements

  • Python 3.14+
  • Either a running Ollama instance with a tool-calling model (e.g. qwen3.5:9b, qwen2.5-coder, mistral-nemo)
  • or a llama.cpp llama-server with Jinja chat templates enabled, which tool calling needs. Current builds enable them by default; on older builds, pass --jinja.

Install

bash
git clone https://github.com/bameschot/momo-coding-harness.git
cd momo-coding-harness
python3.14 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Run

bash
python momo-coding-harness.py                     # TUI + web UI on 127.0.0.1:8765

# a specific project on a remote Ollama
python momo-coding-harness.py --workdir ~/projects/myapp \
    --model qwen3-coder:30b --host http://192.168.1.10:11434

# a local llama.cpp server
python momo-coding-harness.py --provider llamacpp --host http://localhost:8080

The chosen provider is remembered for the next launch, and the status bar shows it as VIA: <provider>. See Running against a backend for step-by-step setups for local and remote Ollama and llama.cpp.

Remote hosts with a token

momo

The token is sent as Authorization: Bearer …. It is never written to disk: not to the session, the log or the input history. It is masked on screen as sk***ere. The host is saved with the session; the token has to be entered again after a restart.

Requirements & footprint

momo is meant to sit beside your editor and use very little of the machine. Nearly all the memory and compute goes to the model, which runs in Ollama or llama.cpp, not in momo.

What you need

  • macOS or Linux. The terminal UI uses Python's built-in curses, which Windows lacks; on Windows, use WSL.
  • Python 3.14+.
  • A model server you can reach: Ollama or llama.cpp, on this machine or another (see Backends).

Dependencies

ollamaThe Ollama clientyes

tree-sitter + 16 grammarsCode navigation and the code index. The grammar wheels are prebuilt and work offline.optional: without them, the code-navigation tools aren't offered

Everything else is Python's standard library: curses for the TUI, http.server for the web UI, urllib for fetch_url, and threading for the background work. The optional HTTPS mode (--web-tls auto) uses the openssl command that macOS and Linux already ship. The web UI is hand-written HTML, CSS and JavaScript with no npm, bundler or CDN. On disk, the dependencies take about 35 MB (18 MB of that is grammars) and the harness itself about 2 MB.

Backends

The harness talks to the model through a small adapter layer (harness/llm/), with one adapter per backend. Both adapters return the same response shape, so modes, tools, streaming, thinking, compaction and both UIs work the same whichever backend you pick. Choose one with --provider ollama or --provider llamacpp. The choice is remembered for the next launch and saved with each session.

By default the compaction threshold is half the detected window. Change it with /context 75%, or set an absolute number with /context 16384 or --context.

Local or remote

"Remote" just means --host points somewhere other than localhost. It can be another machine on your LAN, a GPU box, or a hosted endpoint behind a reverse proxy. The harness, the tools and your files always stay on the machine where you run momo; only the chat requests go to the model server. Always give the full URL, including the scheme: http://192.168.1.10:11434, not 192.168.1.10:11434.

The host is saved with the session and restored when you start again. The token is not saved and has to be entered again.

Tips

  • Prefer an SSH tunnel to exposing the model port. ssh -L 11434:127.0.0.1:11434 gpu-box (or 8080 for llama.cpp) lets momo use the default localhost host, and the server stays unreachable from the network.
  • Traffic to the model is plain HTTP unless your URL is https://. Put a TLS-terminating proxy in front of a remote server you reach over an untrusted network, especially if you send a token.
  • Check the status bar. VIA: ollama or VIA: llamacpp, the host and the model are always visible. The startup message also says which context window was detected.
  • Nothing detected? If the server can't report its window, set one with --context 16384.

Plan mode

1 investigate→2 plan→3 confirm→4 execute
  1. Investigate. The model follows the code path the change touches, tries to reproduce a bug with run_command and finds out how the project is tested. It uses ask_user for questions that would change the plan, one at a time.
  2. Plan. It calls create_plan with a title, a goal and ordered steps. Each step names the file and function it changes, the change itself and how to verify it. The harness writes this to .momo-plan.md.
  3. Confirm. Answer y to run the plan now, or n to keep it for /plan run. Anything else counts as feedback, and the model revises the plan. You can edit .momo-plan.md by hand first. It's re-read on approval, and [-] skips a step.
  4. Execute. The harness runs one step at a time. The plan, with ▶ on the current step, is in the system prompt, so the model knows where it is even after compaction. A step ends with complete_step or a text-only reply. revise_plan replaces the remaining steps and reports any it dropped.

Checkboxes in the file update as steps run: [~] while a step is in progress, [x] when it's done. When the plan is finished, the file is deleted. An interrupt, backend error or exhausted iteration budget pauses the plan. /plan resume, or any message you type, carries on, even after a restart.

Code index

An in-memory index of the working directory, on by default. While it's on, index_callers and index_file replace find_references and file_dependencies, so the model never has to choose between two tools that answer the same question. With /index-route on (the default), plain-text grep_files and find_files calls are answered from the index too.

  • What is indexed: git ls-files -co --exclude-standard in a repo, which respects .gitignore. Binary files and files over 2 MB are skipped.
  • Always current: before answering, the index compares mtimes and sizes and waits for any changes to be indexed. It never answers from a stale index. Edits made by the harness are re-indexed immediately.
  • Memory budget (default 100 MB): when it's over budget, the index drops the text signatures first, then the identifier index, then stops adding files. It says so in every affected result.
  • Safe loading: the pickle loader only accepts the index's own classes, and refuses files that aren't yours or are writable by others.

How the index parses a project

The index is built once in a background thread when you start momo, or when you run /index on. After that it's kept current file by file. Every index_* tool reads from memory; nothing is re-parsed per question except the handful of files a caller search needs.

list files→skip binary & large→parse (tree-sitter)→definitions & imports→identifier occurrences→text signature→keep fresh
  1. List. In a git repository: git ls-files -co --exclude-standard, meaning tracked plus untracked files, with .gitignore respected. That's why a repo with a virtualenv indexes hundreds of files, not thousands. Outside git, it walks the tree and skips .git, node_modules, .venv, other build folders and hidden entries. The cap is 100,000 files.
  2. Skip. The first 4 KB of each file are checked for binary content, and files over 2 MB are left out. Skipped files are remembered by size and modification time, so they aren't read again on every query.
  3. Parse. The file extension picks a tree-sitter grammar, and each file is parsed once. Inline <script> blocks in HTML are parsed as JavaScript at their real line numbers. A file with syntax errors is still indexed, but marked incomplete in results, so a missing hit there isn't taken as proof.
  4. Definitions & imports. The same extractor as code_outline records each definition's kind, qualified name (Class.method), line range, signature and the first line of its docstring or doc comment. It also records the file's imports.
  5. Identifier occurrences. A single tree-sitter query collects every identifier in the file. Each occurrence is stored as a packed (file, line) pair in 8 bytes, and names are shared rather than copied. What a use is (call, definition, import, type or local) is only worked out at question time, and only in the files that contain the name.
  6. Text signature. Each file gets a compact set of the three-letter sequences in its text. index_text uses it to open only the files that could contain the query.
  7. Keep fresh. Before every index_* answer, file times and sizes are compared with the index, and the answer waits until any changes are re-indexed. Files momo edits itself are re-indexed immediately, and run_command triggers a full re-check.

Imports are matched only within a language family (JavaScript/TypeScript/TSX/HTML, C/C++, Java/Kotlin), so java.util.List never resolves to a util.c. Callers come from syntax, not types. Receiver and scope rules remove the usual false hits (self.x in another class, a local that shares the name), but it isn't a type checker and there's no language server. Where it can't be sure, it keeps the hit and labels it.

Internet access

fetch_url is the only tool that sends anything off your machine, so it's off by default and the model isn't even offered it until you turn it on. Neither setting is saved: both reset to the safe default at every launch.

momo
/net on | local | off     # public only · also localhost + LAN · blocked
/net-confirm on|off       # ask before POST/PUT/PATCH/DELETE (default on)
/net-max-bytes 2mb        # download cap
/net-max-chars 24000      # text returned per call; the rest is paged

HTML is converted to readable text, keeping link targets, and JSON is pretty-printed. The model can page through long pages with offset=, jump to a section with find= or pick part of a JSON response with json_path=. Those follow-up calls are served from a short cache.

What is blocked

  • Any scheme except http and https. The client is built without urllib's file, ftp and data handlers.
  • Loopback, private, CGNAT and link-local addresses, unless you use /net local. Every resolved address is checked, so http://2130706433/ and http://127.1/ are blocked too.
  • Redirects into blocked addresses, because every hop is re-checked. Authorization, Cookie and API-key headers are dropped when a redirect changes the scheme, host or port.
  • Credentials in the URL, control characters in URLs and responses, and compressed bodies (so no gzip bombs).
  • Writes to local or private addresses always ask for confirmation, even with /net-confirm off.

Prompt injection and exfiltration aren't solved. Fetched pages are fenced as untrusted content, but small models don't resist injection well. Turn on /run-confirm on while browsing, and keep an eye on the URLs in the transcript.

Web UI

This starts automatically at http://127.0.0.1:8765. It's plain HTML, CSS and JavaScript served by Python's standard-library HTTP server, with no CDN, no web fonts and no build step, and it works fully offline.

One session, two windows

  • Messages, replies, tool calls and diffs appear in both the browser and the terminal.
  • A question from the model can be answered in either window.
  • Mode, model, host, context and plan progress are shared. View options, such as hiding thinking, are per window.
  • Reloading the page replays the conversation so far.

What's in it

  • Status bar: the session drawer, a workspace file browser, mode and model pickers, a CTX meter with a per-category breakdown, and RUN / NET / INDEX badges.
  • Transcript: streamed markdown replies, collapsible thinking, one-line tool calls that expand to show arguments and results, coloured diffs and question cards with Yes/No buttons.
  • Input: / command autocomplete, @ fuzzy path search, a queue for messages sent while the model is busy, and Retry / Edit on your last message.
  • Attachments: drag, paste or pick files. Text and PDFs are converted to text. Chips show a token estimate and turn amber when a file would use more than a quarter of the context.
  • Notifications: a synthesised kitten mew (rising for a question, falling when a turn ends) and an optional desktop notification when the window isn't focused.
  • Syntax highlighting for about 20 languages, copy buttons on code blocks, and light and dark themes.

Access & security

The web UI can do everything momo can, including editing files and running commands in your workspace. So the question is who can reach it. By default the answer is only this computer, and every other setup is something you opt into at startup.

What protects it

  • Loopback by default. momo binds to 127.0.0.1 and rejects any request whose Host header isn't a loopback name. That stops a website you visit from reaching it by pointing its own domain at your machine (DNS rebinding).
  • Same-origin writes. Anything that changes state must be a JSON request from the page itself. Requests from other websites are refused.
  • A token off loopback. On any other address, every request needs the access token. It's generated fresh at each start and never written to disk.
  • Optional HTTPS. This encrypts the token, cookie and conversation. It never replaces the token.
  • No-token mode keeps the Host check. With --web-insecure, only this machine's own names and addresses are accepted, so DNS rebinding stays blocked.

The access token

There's no login form. The token travels inside the URL momo prints, and your browser swaps it for a cookie the first time you open that URL.

Where to find it

The token appears in only one place: the web UI URL momo prints at startup. With 0.0.0.0, the address is replaced by the machine's hostname.

Running asWhere the URL appears
TUI (default)A [system] line near the top of the chat pane: Web UI: http://my-mac.local:8765/?token=Xq3…
--headlessThe terminal it was started from: momo Web UI: http://my-mac.local:8765/?token=Xq3…

The token is everything after ?token=. No command shows it again later. If it has scrolled away, scroll the chat pane back up, restart momo, or use --web-token so you already know it.

In a browser

  1. On the other machine, open the full URL, token included.
  2. momo checks the token and replies with a redirect to / that sets a cookie: momo_token, HttpOnly and SameSite=Strict. The token disappears from the address bar and history, and page scripts can't read it.
  3. From then on the cookie authorises every request, so bookmark plain http://my-mac.local:8765/ (https:// when HTTPS is on).

If the hostname doesn't resolve on the other machine (it relies on .local / mDNS or your DNS), replace it with the machine's IP address and keep the token: http://192.168.1.20:8765/?token=Xq3….

From scripts

Scripts don't need the cookie: send the token as a Bearer header on every request.

bash
TOKEN=Xq3…      # the part after ?token=
curl -s -H "Authorization: Bearer $TOKEN" http://my-mac.local:8765/api/state | jq .status
curl -s -X POST http://my-mac.local:8765/api/submit \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"text": "/context"}'

HTTPS

With a certificate the device trusts, the page counts as a secure context on other devices too, so desktop notifications and the copy buttons' clipboard access work over the LAN. Browsers block both on plain-HTTP LAN addresses.

momo's own certificate: --web-tls auto

bash
python momo-coding-harness.py --web-host 0.0.0.0 --web-tls auto
output
Web UI: https://my-mac.local:8765/?token=Xq3…
HTTPS: trust momo's local CA once per device — ~/.momo-harness/tls/momo-ca.pem
       (also at https://my-mac.local:8765/momo-ca.pem), SHA-256 97:9A:56:…
  1. First start: momo creates a small certificate authority and a server certificate for localhost, your hostname, <hostname>.local and this machine's LAN addresses. They're stored in ~/.momo-harness/tls/, readable only by you. It needs just the openssl command; macOS's built-in one works. Add extra names or a VPN address with --web-tls-name.
  2. Trust the CA once per device. Download /momo-ca.pem from the running server (no token needed; a CA certificate is public), check that its SHA-256 fingerprint matches the one momo printed, and install it:
    DeviceHow
    macOSOpen it in Keychain Access, then set When using this certificate to Always Trust
    iOS / iPadOSInstall the downloaded profile, then enable it under Settings → General → About → Certificate Trust Settings
    AndroidSettings → Security → Encryption & credentials → Install a certificate → CA certificate
    LinuxCopy it to /usr/local/share/ca-certificates/momo-ca.crt and run sudo update-ca-certificates. Firefox has its own store: Settings → Certificates → Import.
    WindowsOpen it and install it into Trusted Root Certification Authorities
  3. Open the printed URL and use the token as usual. If you skip step 2, the connection is still encrypted, but the browser shows a certificate warning.

Later starts reuse the certificate. When your IP address or hostname changes, momo issues a new server certificate by itself, and devices that already trust the CA don't need to do anything.

The CA can only vouch for localhost, *.local, your hostname, loopback and private addresses (including Tailscale's 100.64.0.0/10), and names given when it was created. This is enforced with X.509 name constraints. A device that trusts it can't be tricked into accepting a certificate for a public site, even if momo-ca.key leaks. Keep that key private anyway.

Your own certificate

bash
python momo-coding-harness.py --web-host 0.0.0.0 --web-cert my-mac.pem --web-key my-mac-key.pem

If the certificate or key can't be loaded, momo says so at startup: Web UI failed to start …, and --headless exits with an error.

Behind a reverse proxy

Keep momo on loopback, but give it a fixed token. That switches on token mode, which lets the proxy pass its own Host header:

bash
python momo-coding-harness.py --web-host 127.0.0.1 --web-token "$(openssl rand -hex 16)"
Caddyfile
momo.example.com {
    reverse_proxy 127.0.0.1:8765
}
nginx
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_set_header Host $host;   # the Origin check compares against it
    proxy_buffering off;           # /api/events is Server-Sent Events
    proxy_read_timeout 1h;
}

Then open https://momo.example.com/?token=<token> once. Never let the proxy strip the Origin header: a missing Origin passes the same-origin check, so any website could then send commands to momo.

No token: --web-insecure

--web-host 0.0.0.0 --web-insecure serves plain HTTP without generating or asking for a token. momo prints a warning with the URL, because anyone who can reach the address can read the conversation and run commands as you. Use it only on a network where you trust every device. The Host check stays on: only this machine's own names and addresses are accepted, plus any you add with --web-allow-host. So a website you visit still can't drive momo.

Keep it safe

  • Treat the token like a password. Anyone with it controls momo, and it sits in your terminal scrollback.
  • Prefer the SSH tunnel for your own machines: nothing is exposed, and no token is needed.
  • Over plain HTTP the token and cookie are visible on the network. Use HTTPS on anything but a network you trust.
  • Keep ~/.momo-harness/tls/momo-ca.key private. It's limited to local names by design, but it's still a key your devices trust.
  • Turn on /run-confirm on when others can reach the UI, or when browsing with /net on, so no shell command runs unseen.

Context & compaction

At startup the harness detects the model's native context window and uses half of it as the working limit. Override it with --context or /context. The CTX meter turns yellow at 75% and red at 90%.

When usage passes the limit, compaction runs on the worker thread:

  1. Old tool-call groups are removed first, oldest first.
  2. Then whole old turns.
  3. Then the largest remaining tool results are trimmed.

The dropped history is summarised by the model into a single summary block. The system prompt, the question currently being worked on and its latest tool results are never dropped. /fast-compact skips the summary.

Sessions

Sessions auto-save after every reply to ~/.momo-harness/sessions/<timestamp>.json, including the model, host, mode, workdir, context settings, active skills, input history and messages. The auth token is the one thing deliberately left out. An NDJSON .log alongside records every request, response, tool call and token count.

Skills & project guides

Skills are Markdown files in skills/ that are appended to the active role prompt. They stack, are saved with the session and survive mode switches.

momo
/list-skills
/load-skill python
/unload-skill python

Built in: bash, c, code-review, data-analysis, document-editing, html-javascript, java, kotlin, maven-dependency-updates, python, rust, software-design, sql, storytelling, tdd, text-based-game-design, typescript. To add your own, drop a .md file into the folder.

Project guides (/guides on) load the workdir's AGENTS.md, CLAUDE.md, MOMO.md, GEMINI.md, .github/copilot-instructions.md or .cursorrules into the system prompt, where compaction can't drop them. They're re-read on a new session, /clear, compaction and workdir changes.

The companion

momo is the ASCII cat walking along the top of the input box, in both the TUI and the browser. It walks, sits, blinks and mews lines that fit the current mode and whether the model is busy. Shift+Q or /companion off hides it.

With /companion-idle-recap on, a companion left alone for 90 seconds (configurable) recaps what you just did instead of saying its canned lines. It does this at most once per turn, with a cooldown.

The cat at the bottom of this page is a standalone copy of it. On this page it quotes whichever section you're reading. Click it to make it talk.

Tests & evals

bash
python -m unittest discover tests                 # do the tools work?
python evals/run_evals.py --runs 3                # does the model use them? (needs a server)

tests/ uses the standard-library unittest. It includes one fixture per tree-sitter grammar, so a grammar upgrade that renames a node fails a test instead of silently emptying a tool's output. evals/ asks questions with known answers and scores whether the model reached the right tool, how many calls it took and how much output it pulled into context. Sampling isn't pinned, so read the min–max spread, not a single run.
